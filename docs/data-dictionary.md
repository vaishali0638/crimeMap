# CRIMEMAP Data Dictionary

> Phase 0 logical model. Physical DDL is produced as Alembic migrations in Phase 2. Column names are
> snake_case. Classification column: I = INTERNAL, R = RESTRICTED, HR = HIGHLY_RESTRICTED.

## Conventions

- Primary keys: `id uuid` (UUIDv7, time-ordered for index locality), generated by the application.
- Audit columns on mutable tables: `created_at timestamptz`, `updated_at timestamptz`,
  `created_by uuid → app_user.id`, `updated_by uuid → app_user.id`.
- Table names avoid PostgreSQL reserved words (the specification's **User** entity is `core.app_user`,
  because `user` is reserved and would require quoting everywhere).
- All timestamps `timestamptz`, stored in UTC, displayed in Asia/Kolkata (IST).
- Geometry: `geometry(<type>, 4326)` with GiST index; metric work in region CRS (ADR-005).
- Enumerations implemented as PostgreSQL enums or check-constrained text (decided per table in Phase 2).
- Soft delete only where stated; otherwise records are immutable or versioned.
- Every scoped table carries `region_id` and `station_id` (denormalised) so RLS policies stay simple and
  indexable.

## Schemas

| Schema | Purpose | App role access |
|---|---|---|
| `core` | Operational and analytical data | `crimemap_app` read/write through RLS |
| `restricted` | HIGHLY_RESTRICTED source details | No grant to `crimemap_app`; separate audited service role |
| `staging` | Raw ingest, dead letter | Worker only |
| `audit` | Audit events | Insert-only for app/worker; read for audit service |

## 10. `core.analyst_note` (R)

id, subject_type (INCIDENT / CELL / PATTERN_REVIEW / ACTION / DQ_ISSUE), subject_id, note (text, max
4000, rendered escaped), visibility_level, evidence_links jsonb, region_id, station_id, created_by,
created_at. Append-only: the API role has INSERT and SELECT only. RLS limits reads to the caller's
territory, and since migration 0006 the author must be the session user (Phase 3). A CELL note
carries the region and the station that holds the cell's centre.

## 11. `core.operational_record` (R)

Supplementary records from the "+ Add Operational Record" modal — **never an FIR**.
id, record_kind (ANALYST_NOTE / LOCATION_CORRECTION_REQUEST / APPROVED_EVENT_MARKER /
OPERATIONAL_OBSERVATION / ACTION_COMPLETION / CIVIC_CONTEXT_REFERENCE), title, occurred_at, geometry,
precision_level, confidence, reason, evidence_reference, visibility_classification, review_status
(NOT_REQUIRED / PENDING / APPROVED / REJECTED), reviewed_by, region_id, station_id, audit columns.

As built (Phase 3):
- There is no column or foreign key that could write to `incident_record`. A
  LOCATION_CORRECTION_REQUEST names `subject_incident_id` only as a reference.
- New records start PENDING for corrections, event markers and civic references, and NOT_REQUIRED
  for the other kinds.
- A CHECK ensures `reviewed_by <> created_by`. A trigger allows the review decision to be set only
  once and leaves the other columns immutable.
- CIVIC_CONTEXT_REFERENCE is refused (503) while the civic flag is off. ACTION_COMPLETION is refused
  (422) until Phase 6 builds actions.
- RLS restricts rows to the caller's territory.

Database-enforced since migration 0006 (Phase 3 audit), so not only the API keeps these rules:
- A new record starts PENDING or NOT_REQUIRED according to its kind, without a reviewer.
- Its author is the session user (`app.user_id`).
- A referenced incident must be visible to the session (RLS) and in the same region.
- A decision goes from PENDING to APPROVED or REJECTED only, once, by a session user other than the
  author, with `reviewed_at` set. CHECK `operational_record_decision_has_reviewer` keeps the status
  and the reviewer consistent.

## 12. `core.data_quality_issue` (I/R)

id, incident_id (nullable), subject_type, subject_id, issue_type (MISSING_LOCATION / LOW_CONFIDENCE_LOCATION
/ MISSING_OCCURRENCE_TIME / POSSIBLE_DUPLICATE / INVALID_CATEGORY_MAPPING / STALE_SOURCE / OUTSIDE_JURISDICTION
/ OTHER), severity (LOW / MEDIUM / HIGH), detected_by (RULE / AI / USER), rule_code, state (OPEN /
ASSIGNED / RESOLVED / ACCEPTED_AS_IS), assigned_to, due_at, resolution_note, detail (jsonb: rule
facts such as confidence or, for DQ-DUP-001, the partner's internal id — never a case reference or personal data), region_id, station_id,
created_at, updated_at. Unique (subject_type, subject_id, rule_code). Rules and their codes are in
[demo-data.md §4](demo-data.md). The API role may change only state, assigned_to, resolution_note

`USER-<issue_type>` and `detail = {"reason": …}` through the API's INSERT grant on the creation
columns (Phase 3). Since migration 0006 a restrictive policy allows the API role to insert only
USER issues about an incident, in that incident's region, with a `USER-` rule code.

## 22. Lineage

Every `incident_record` traces to `source_record_link` → `staging.raw_ingest` (payload hash) →
`source_system`, plus the category mapping version and boundary version used for enrichment.
Re-ingesting the same payload produces the same idempotency key and no new rows.
